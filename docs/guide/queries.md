# Read data through application tables

The examples below describe the existing default compiler. The hierarchical
model supports compilation and fetch/count execution of physical SELECTs, to-one relations, SQL formulas,
formula methods, alias columns and correlated subqueries (`select`, `exists`,
`select_*`, `subQueryColumn`, including `subquery_*` method references). Table
aliases and local parameter namespaces remain separate across recursive SELECTs.
JSON/XML subQueryColumn aggregation remains PostgreSQL-only. Native row filters, star expansion, PERIOD and IN_RANGE, bagItemColumn and
explicit grouping/distinct are connected. IN_RANGE puts typed comparisons before
NULL checks, allowing PostgreSQL to bind absent bounds without changing the four
legacy interval cases.
The hierarchical compiler also supports `compiler.count(...)`: it emits
`COUNT(*) AS "gnr_row_count"` for plain queries, group keys for GROUP BY,
and the original projection for DISTINCT, following the legacy count branch.
On this path, `query.count()` interprets those results as the legacy terminal did:
it reads `gnr_row_count` for ordinary counts and counts rows for GROUP BY/DISTINCT.
`query.fetch()` returns mutable Toolbox NamedList rows through the owning database
connection. Both terminals recompile in the current environment, without a result
cache or implicit commit. See {download}`the terminal report <../design/92-hierarchical-fetch-count.md>`.
Star uses the native model's column order, which may differ from legacy XML
for fields generated by sys_fields. XPath bagItemColumn remains PostgreSQL-only.
On the hierarchical path, `addPkeyColumn=True` appends the primary key as `pkey`
for non-aggregate queries; its default is False (only requested columns). To-many
navigation is not yet supported: relation operation calls are recognized, but
no `many_*` handler is implemented. The hierarchical `TreeQueryCompiler` also
preserves legacy symbolic parameters in WHERE; this differs from the existing
`QueryCompiler` (see [symbolic parameters](#symbolic-parameters-and-external-values)).
Its subsequent SQL preparation, also used by `db.execute(sql, params)`, follows
the legacy adapters and retains unused mapping entries; see
{download}`the R3 report <../design/83-legacy-realignment-r3.md>`.
Raw SQL execution does not perform model-aware symbolic parameter expansion.

Start with a database built from a `SqlDatabaseConfig` recipe. Except for the self-contained PERIOD and symbolic-parameter examples, examples on
this page use the `sales.customer`, `sales.invoice` and `sales.line` model in the
[tutorial](tutorial.md). They assume its physical tables and seed data exist.
Execution examples explicitly commit on success and roll back on failure, including reads.

## Compile without executing

Construction and compilation only need the completed model; physical tables and
seed data are not required for this example:

```python
query = db.table("sales.invoice").query(
    columns="$id, COALESCE($total, 0) AS total",
    where="$total >= :minimum",
    minimum=100,
)
compiled = query.compiled
sql = compiled.sql
kwargs = dict(compiled.params)
```

No connection is opened and no SQL is executed. PostgreSQL output uses psycopg
`%(name)s` placeholders; SQLite uses `:name`. Ordinary bound values stay separate
from SQL; symbolic WHERE parameters on the hierarchical path are described below.
Read `compiled` once to capture SQL and parameters from the
same compilation: a later access recompiles against the current environment.
Literal percent signs in PostgreSQL SQL are escaped for execution with the
parameter mapping. Do not format or interpolate that SQL yourself.

The query can be reused; compilation does not overwrite its original arguments.
Collection parameters and subquery scopes use the existing name allocator to
avoid collisions. This does not yet add chained `.query(...)` or set operators.

## Select, filter and order

```python
try:
    invoice = db.table("sales.invoice")
    rows = invoice.query(
        columns="$id, @customer.name AS customer_name, $total",
        where="$total >= :minimum",
        minimum=100,
        order_by="$total DESC, $id",
        limit=20,
    ).fetch()
    db.commit()
except Exception:
    db.rollback()
    raise

```

`rows` is a list of mutable `genro_toolbox.NamedList` objects on PostgreSQL and
SQLite. With the tutorial data, `dict(rows[0])` is:
`{'id': 10, 'customer_name': 'Ada', 'total': Decimal('125.00')}`.
The decimal value comes from PostgreSQL numeric adaptation; it is not a float.

A query is lazy. Constructing it validates some options but does not execute
SQL; model references and expressions are compiled when you inspect or execute
it. Each `.fetch()` or `.execute()` compiles and executes again.

Rows follow the legacy named-list contract:

```python
row = rows[0]
assert row['id'] == row[0]
row['customer_name'] = 'Local edit'
assert row[1] == 'Local edit'
row[1] = 'Another local edit'
mapping = dict(row)
```

Names follow the SELECT projection order, including explicit aliases. Negative
indices and slices work like lists; iteration yields **values**. `keys()`,
`items()`, `values()`, `get()` and `update()` expose the legacy named interface.
`'id' in row` tests for a column name. Equality is list equality; compare
`dict(row)` with a dictionary. For JSON objects, serialize
`[dict(row) for row in rows]`; serializing rows directly produces arrays.

Rows fetched from one cursor share a column index. Adding a local named column updates
that index; other rows can still have shorter value lists and return None for
the new name until assigned. This is the legacy behavior. Structural list
operations such as deletion or reordering do not repair the column index.
Separate fetches have separate indices and fresh values. Local edits never
write to the database. `record.output('dict')` continues to return a detached
dictionary. Streaming, Selection and Python-column evaluation remain separate.

| Option | Meaning and default |
|---|---|
| `columns` | Projection string or sequence; `'*'` by default. |
| `bagFields` | `False`; include physical X columns in wildcard SELECTs when true. |
| `where` | Trusted SQL predicate using model references and value parameters. |
| keyword bindings | Bound values as keyword arguments (`minimum=100`), or the `sqlparams={...}` mapping. |
| `order_by` | SQL ordering expression using model references. Tables have no default ordering: without `order_by` the row order is not guaranteed. |
| `limit`, `offset` | Nonnegative integers; `limit=0` returns no rows. |
| `for_update` | `False`; when true, lock base-table rows until transaction completion. |
| `exclude_draft` | `True`; applies a declared draft policy. |
| `exclude_logical_deleted` | `True`; also accepts `False` or `'mark'`. |
| `ignore_partition` | `False`; enforce declared partition scopes. |

The table is chosen by `db.table(...)`, not by a query option. Short names such
as `'invoice'` work only when unambiguous. Use qualified names in reusable code.
[Row policies](row-policies.md) explains the last three options. Their camel-case
spellings `excludeDraft`, `excludeLogicalDeleted` and `ignorePartition` are also
accepted; do not supply both spellings of the same option.

## Read the expression vocabulary

| Syntax | Meaning | Example |
|---|---|---|
| `$name` | Local logical column, including a declared virtual column. | `$total >= :minimum` |
| `@relation.column` | Column reached through a declared forward or inverse relation. | `@customer.name` |
| `AS name` | Result column name for named access. | `$id AS invoice_id` |
| `:name` | Bound data value. | `minimum=100` |
| `:env_name` | Explicit parameter, or environment fallback for `name`. | `:env_customer_id` |
| SQL expression | Trusted PostgreSQL expression. | `COALESCE($total, 0) AS amount` |

A direct column keeps its logical name. A relation projection defaults to a
path-derived name such as `customer_id_name` for `@customer_id.name`; prefer explicit `AS` when defining
a public result shape. Give computed projections explicit aliases for clarity.
Result names must be unique.

For unusual logical column names use `$"display name"`; double embedded quotes,
as in `$"a""b"`. Result aliases containing spaces also need double quotes.
Quoted SQL strings, comments, quoted identifiers and dollar-quoted bodies protect
their contents from reference expansion.

`*` expands physical columns first, then virtual columns marked `static=True`,
as in legacy `starColumns`. Physical XML/Bag columns (`dtype="X"`) are omitted
unless `bagFields=True`; explicitly named columns remain available. Static virtual
X columns are included in either mode. Unsupported static columns fail explicitly.
Prefer explicit projections for stable result contracts. `record()` keeps
`bagFields=True` by default, as in the legacy record compiler; passing False
explicitly omits physical X fields.

## Legacy filter macros

`#IN_RANGE(value, low, high)` is supported in query WHERE clauses and in the
SQL formula columns, including native packages. Bounds are inclusive; a NULL
bound leaves that side open, and two NULL bounds mean true even for a NULL
value. Arguments retain the legacy simple field/path/parameter syntax.

```python
compiled = db.table("sales.invoice").query(
    columns="$id",
    where="#IN_RANGE($total, :minimum, :maximum)",
    minimum=100, maximum=None,
).compiled
```

`#PERIOD(field, :period)` is supported in query WHERE clauses, including WHERE
in the already-supported scalar subquery route. The colon before the period
parameter is optional. It uses the existing Toolbox period parser and the
application's `workdate` and `locale` environment values. Toolbox 0.17 provides
English and Italian language data; unsupported locales fail explicitly.

This independent, compile-only example declares its own DATE column `issued`:

```python
from datetime import date
from asqueel import SqlDatabaseConfig, build_database

period_config = SqlDatabaseConfig()
period_package = period_config.source.db('period_example').packages().package('sales')
period_invoice = period_package.table('invoice', pkey='id')
period_invoice.column('id', dtype='L')
period_invoice.column('issued', dtype='D')

with build_database(period_config) as period_db, period_db.tempEnv(
    workdate=date(2026, 10, 14), locale="it"
):
    compiled = period_db.table("sales.invoice").query(
        columns="$id", where="#PERIOD($issued, period)", period="mese scorso",
    ).compiled
    sql, kwargs = compiled.sql, dict(compiled.params)
    # The generated bounds are date(2026, 9, 1) and date(2026, 9, 30).
```

The period text is consumed during compilation; only the resulting date bounds
are bound. As in the legacy, a single day uses equality, a closed interval uses
inclusive BETWEEN, an open interval uses >= or <=, and an empty period uses
true. Commas remain legacy range separators. Generated names keep the legacy
`period_from`/`period_to` base and are disambiguated when the caller already uses
those names. This is not an automatic whole-day timestamp conversion.

Macro contexts are intentionally limited: PERIOD is not a direct SELECT or
ORDER BY expression; GROUP BY/HAVING do not receive general macro expansion.
Quoted strings and comments remain unchanged. Unavailable macros report their
name instead of being sent unexpanded to the server. ENV/PREF, BAG/BAGCOLS,
full-text/vector macros and a custom macro registry are not implemented here.
Existing `:env_name`, correlated `#THIS` and named subquery references retain
their current behavior. Native package SQL formulas and `var_*` locals are
supported, including native select/exists/select_* and sql_formula_<name>(attr)
methods on the existing application table class. RuntimeModel remains a later step.

## Bind values, including collections

```python
try:
    rows = db.table("sales.customer").query(
        columns="$id, $name",
        where="$name ILIKE :pattern",
        pattern="%ad%",
        order_by="$id",
    ).fetch()
    db.commit()
except Exception:
    db.rollback()
    raise

```

On SQLite, both compiler profiles translate the `ILIKE` operator to SQLite's
`LIKE` in the adapter. Column names such as `ilike_label`, quoted strings and
parameter names are left unchanged by this translation. Matching follows
SQLite's `LIKE` semantics.

In the existing `QueryCompiler`, parameters bind values, not identifiers or SQL
fragments. Missing parameters raise an error; unused entries in an explicit
`sqlparams` mapping are omitted from the compiled statement. The hierarchical
`TreeQueryCompiler` preserves legacy symbolic WHERE parameters instead; see
[symbolic parameters and external values](#symbolic-parameters-and-external-values).
Choose ordering and column expressions from application-controlled options.
Do not interpolate external values into SQL.

The shorthand `query(where='$id=:wanted', wanted=1)` is supported. Unknown
keywords that are not consumed as parameters fail, helping catch misspelled
query options. Prefer the explicit mapping for reusable application code.

For PostgreSQL list membership, use `ANY` with a Python list:

```python
try:
    rows = db.table("sales.customer").query(
        columns="$id, $name", where="$id = ANY(:ids)",
        ids=[1, 2], order_by="$id",
    ).fetch()
    db.commit()
except Exception:
    db.rollback()
    raise

```

An empty array matches no rows. For the PostgreSQL `ANY` expression, use a cast
such as `:ids::bigint[]` if the surrounding SQL cannot infer the array type.
Lists containing `None` retain PostgreSQL NULL semantics.

`IN :ids` and `NOT IN :ids` bind a collection. The compiler binds one parameter
per member and never interpolates values into the SQL text. The rules:

- Accepted values are `list`, `tuple`, `set` and `frozenset`. Any other value
  after `IN`/`NOT IN` — including `str`, `bytes`, `int` and `dict` — raises
  `ValueError` naming the parameter, before any SQL is sent.
- Members are bound in order and duplicates are kept, not deduplicated.
- A `None` member is bound as NULL and SQL three-valued logic applies:
  `$id IN :ids` with `ids=[1, None]` matches only `id` 1, and `$id NOT IN :ids`
  with the same list matches no row at all, because `x <> NULL` is never true.
- An empty collection renders an operand-free form that matches no rows for
  `IN` and every row for `NOT IN`, rows whose column is NULL included: `= ANY('{}')` / `<> ALL('{}')` on
  PostgreSQL, `IN (SELECT 1 WHERE 0)` / `NOT IN (SELECT 1 WHERE 0)` on SQLite.
  `IN ()` is never emitted.
- The same parameter used in collection position twice expands both
  occurrences. The same parameter used once in collection position and once in
  scalar position — `$id IN :ids AND $other = ANY(:ids)` — raises `ValueError`
  naming it, in either order, subqueries included.
- A list used only in scalar position keeps its existing binding: on PostgreSQL
  `= ANY(:ids)` still binds one array parameter, the empty list included.

`db.execute(sql, {...})` uses legacy text preparation. Collections are `list`,
`tuple`, or `set`; SQLite generates `name0`, `name1`, etc., while PostgreSQL
uses the legacy postgres3 `name_0`, `name_1` expansion. These generated names
can overwrite existing names, as in the legacy adapters. PostgreSQL's empty-IN
rule recognizes the qualified `"t0"."field"` form, rather than arbitrary SQL.
Unused kwargs remain. Missing ordinary bindings become `None` (SQL NULL) in
the prepared kwargs, without replacing the SQL placeholders; explicit values
keep precedence. Invalid scalar IN operands are left to the driver.
Use `\:` for a literal colon and `%%` for a literal percent
in PostgreSQL SQL text. Parameter values themselves need no such SQL escaping.
See {download}`the R3 contracts and tests <../design/83-legacy-realignment-r3.md>`.

Use `IS NULL` for a NULL test. `column = :value` with `value=None` does not mean
`IS NULL`. PostgreSQL casts such as `:minimum::numeric` are preserved.
PostgreSQL still needs a type for a parameter used only in `IS NULL`, including
an explicit `None`: use a typed expression such as `CAST(:value AS TEXT) IS NULL`.
Preparation does not insert casts automatically.

## Symbolic parameters and external values

The two compiler profiles differ intentionally here. `QueryCompiler` is the
existing compiler selected by the default native render. `TreeQueryCompiler`
compiles the hierarchical model produced by `render(mode='objects_tree')`.

This self-contained example builds both profiles from the same recipe. It only
compiles queries; no connection or physical table is required:

```python
from asqueel import SqlDatabase, SqlDatabaseConfig

symbolic_config = SqlDatabaseConfig()
symbolic_root = symbolic_config.source.db('symbolic', implementation='sqlite')
symbolic_root.connection('main', database=':memory:')
document = symbolic_root.packages().package('app', sqlschema='main').table(
    'document', pkey='id',
)
document.column('id', dtype='L')
document.column('name', dtype='T')
document.column('owner', dtype='T')
symbolic_native = symbolic_config.render()
symbolic_tree = SqlDatabase(
    model=symbolic_config.render(mode='objects_tree'), config=symbolic_native.config,
)
native_compiled = symbolic_native.table('app.document').query(
    columns='$id', where='$name=:wanted', wanted='$owner',
).compiled
query = symbolic_tree.table('app.document').query(
    columns='$id', where='$name=:wanted', wanted='$owner',
)
compiled = query.compiled
```

| Compiler | Meaning of the WHERE condition | SQLite WHERE output |
| --- | --- | --- |
| Existing `QueryCompiler` | Compare `name` with the literal string `$owner` | `"t0"."name"=:wanted` |
| Hierarchical `TreeQueryCompiler` | Compare `name` with the value of column `owner` | `("t0"."name"="t0"."owner")` |

Both compiled mappings retain `{'wanted': '$owner'}` in this example. On the
hierarchical path that entry is no longer used by the WHERE expression. On
PostgreSQL the same distinction applies; remaining bindings use `%(wanted)s`.
Compilation does not modify the original query arguments.

This is the legacy `embedFieldPars` behavior, applied to WHERE before collecting
field references. A string starting with `$` is substituted only when the rest
names a physical or virtual column of the current table. A string starting with
`@` is eligible when its first relation segment exists in that table; the
remaining path must then resolve through the model. Bytes are decoded before
this check. Strings not recognized as references remain bound values. This is
not arbitrary SQL-fragment substitution and does not apply to all clauses.

For a literal value beginning with `$` or `@` on the hierarchical path, use the
existing legacy escape convention:

```python
query = symbolic_tree.table('app.document').query(
    columns='$id', where='$name=:wanted', wanted=r'\$owner',
)
literal_compiled = query.compiled
symbolic_tree.close()
symbolic_native.close()
```

Here WHERE keeps its placeholder. Later, adapter argument preparation removes
the leading backslash, so the bound value is the literal string `$owner`.
The same convention applies to `r'\@customer.name'`. Do not apply this escape to
the existing `QueryCompiler`: it retains the backslash in the bound value.

For browser or other external input, putting a value in `sqlparams` or query kwargs
therefore does **not** guarantee literal binding on the hierarchical path.
Validate input against the expected field/domain and distinguish literal data
from intentional model references. When a literal string starts with `$` or `@`,
use the legacy escape above on that path. Without it, a value matching a model
reference can change a comparison from column-to-value to column-to-column.
SQL expressions, column choices and ordering still require application control;
no optional SQLGlot check is integrated into the core.

Raw `db.execute(sql, params)` has no table-aware `embedFieldPars` step: `$owner`
in its parameter mapping stays a value. Its legacy adapter preparation does
remove the `\$` / `\@` escape, however. Both raw preparation and the hierarchical
path fill missing ordinary bindings with `None` (SQL NULL) and retain unused
mapping entries. The existing `QueryCompiler` instead rejects missing bindings
and omits unused entries, as described above.

## Navigate relations without writing joins

```python
try:
    rows = db.table("sales.invoice").query(
        columns="$id, @customer.name AS customer_name",
        where="@customer.name = :name", name="Ada",
        order_by="$id",
    ).fetch()
    db.commit()
except Exception:
    db.rollback()
    raise

```

The relation is declared by the model, and its target must be a recognized
primary or unique key. The compiler creates a LEFT JOIN and reuses it for the
same path across projections, filters and ordering. A missing target produces
NULL values. A WHERE condition on the target can still exclude that row.

Relations can be chained, using `@customer.@country.name` or
`@customer.country.name` when those relations exist. Ordinary inverse paths
declared with `inverse` or `back_reference` also use LEFT JOIN: the unique key
is on their source side, and the target can contain several matching rows.
The same path reuses its join across projections, filters and ordering.

For example, projecting `@lines.amount` returns one SQL row per matching
line, with NULL when there are no lines. It does not produce a Python list
of amounts. Use explicit SQL aggregates and GROUP BY, a declared scalar
subquery, or `distinct=True` according to the required result. `count()`
counts the SQL result rows; there is no implicit DISTINCT or parent grouping.
Virtual relations remain pending. Related-table policies are not automatically
added to a plain join; the root table's policies govern the query.

## Use relations, formulas and aggregates

```python
try:
    rows = db.table("sales.invoice").query(
        columns="$id, @customer.name AS customer_name, $double_total, $line_total, $has_lines",
        order_by="$id",
    ).fetch()
    db.commit()
except Exception:
    db.rollback()
    raise

```

`customer_name` is the result name for the related column `@customer.name`;
`double_total` is a SQL expression; `line_total` and `has_lines` are correlated
formulas. Their declaration and scope rules are in [models](models.md) and
[formulas](formulas.md). They are read-only.

For a count, use an explicit SQL aggregate:

```python
try:
    rows = db.table("sales.invoice").query(columns="COUNT(*) AS n").fetch()
    count = rows[0]["n"]
    db.commit()
except Exception:
    db.rollback()
    raise

```

With the existing default compiler, `query.count()` returns a Python `int`
computed by the database with one statement. When the query projects only column references and carries no
`distinct` or `group_by`, it renders `SELECT count(*) ... FROM`; otherwise it
wraps the select in a subquery, so `count()` always equals `len(fetch())`.
ORDER BY is dropped from the count statement and `for_update=True` is ignored.
Row policies are applied exactly as for `fetch()`. `count()` on a query with a
`limit` or an `offset` — `0` included — raises `UnsupportedFeatureError`
mentioning limit/offset, before any SQL is sent. `count()` does not mutate the
query: its options, params and compiled SQL are unchanged afterwards.

With the hierarchical model, count follows the legacy algorithm instead: plain
queries become COUNT(*), GROUP BY projects the group keys, and DISTINCT keeps its
projection. The terminal reads the scalar count or counts the returned rows as
appropriate. LIMIT/OFFSET are retained; an offset can remove the single COUNT(*)
row and yield zero. An aggregate projection without GROUP BY or DISTINCT becomes
COUNT(*), so equivalence with `len(fetch())` is not imposed. Fetch and count still
leave the query unchanged and run within the owning database transaction.

`distinct`, `group_by` and `having` express uniqueness and grouping:

- `distinct=True` adds DISTINCT; `False` and `None` add nothing. Any other
  value, `''` and `1` included, raises `ValueError` mentioning `distinct`.
- `group_by` and `having` are expressions resolved like `where`: fields,
  forward/inverse paths, alias columns and formulas resolve, a repeated relation reuses
  its join, and collection parameters work in `having`.
- `group_by='*'` raises `UnsupportedFeatureError`; project the aggregate
  explicitly instead.
- `having` without `group_by` raises `UnsupportedFeatureError` naming both.
- `for_update=True` with `distinct` or `group_by` raises
  `UnsupportedFeatureError`, as does `exclude_logical_deleted='mark'` with
  either of them.
- With DISTINCT, every ORDER BY item must name a projection alias or resolve to
  a projected expression; anything else raises `UnsupportedFeatureError`
  mentioning ORDER BY, on both backends.
- DISTINCT projects only the requested columns: no primary key and no policy
  column is added. There is no Python-side grouping or deduplication, and
  DISTINCT ON is not available.

Counting grouped results is different from counting base rows: define the query
shape before choosing its terminal. An SQL aggregate does not assemble related
collections; those have an explicit result shape.

## Fetch exactly one record

```python
try:
    customer = db.table("sales.customer")
    reader = customer.record(1)
    first = reader.output("dict")
    again = reader.output("dict")  # A copy of the same cached snapshot.
    immediate = customer.record(2, mode="dict")
    db.commit()
except Exception:
    db.rollback()
    raise

```

`record()` enforces exactly one visible match. It raises `RecordNotFoundError`
for no match and `RecordMultipleRowsError` for several. It is not a `fetch()[0]`
shortcut that silently ignores additional rows.

Supply a complete key mapping or an ordered sequence for composite primary keys.
A scalar is accepted for a single-column key, including zero. Key values cannot
be `None`. Alternatively, supply `where` and `params` for a unique selector.
Record reads select the complete resolved row; custom projections, `limit` and
`offset` are rejected. Use `query()` for partial rows.

`reader.refresh()` discards and reloads its snapshot in the current environment.
A reader does not automatically refresh after a write, commit or scope change.
Choose a record output for the consumer: dictionary data, a Bag representation
or serialized data. A Selection adds result operations and metadata around a
query result, rather than turning a table into a tracked row object.

## Inspect SQL and result metadata

```python
query = db.table("sales.invoice").query(
    columns="$id, $total", where="$id=:wanted", wanted=10,
)
compiled = query.compiled  # No connection required.
print(compiled.sql)
print(dict(compiled.params))

try:
    result = query.execute()
    assert result.rows[0]["id"] == 10
    assert [column.name for column in result.columns] == ["id", "total"]
    db.commit()
except Exception:
    db.rollback()
    raise

```

`QueryResult` has `rows`, `rowcount` and `columns`. Direct model projections carry
dtype, UI and source identity metadata. Arbitrary SQL expressions do not acquire
inferred dtype or UI metadata. Results are fully materialized; pagination limits
memory use when fetching large datasets.

`compiled.sql` is prepared for the driver, not for Python string interpolation.
Parameters may contain sensitive application data; log selectively. For direct
execution and parameter formatting, see [the compiler interface](compiler.md).

## Lock rows during a change

```python
try:
    row = db.table("sales.customer").record(1, for_update=True).output("dict")
    db.table("sales.customer").update({"id": row["id"], "name": "Ada Lovelace"})
    db.commit()
except Exception:
    db.rollback()
    raise

```

PostgreSQL locks only the base table with `FOR UPDATE OF`. Locks end at commit or
rollback. A cached reader does not acquire a new lock in another transaction;
use a fresh reader or refresh it. PostgreSQL rejects locking incompatible SELECT
forms, including aggregate projections.
