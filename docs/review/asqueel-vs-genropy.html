Design review · for the GenroPy team

Asqueel and GenroPy SQL

Asqueel is the port of GenroPy's SQL layer to a standalone library. This document describes Asqueel as it will look when the decisions below are implemented, compares each part with GenroPy's SQL layer, and asks the team to challenge the choices.

Date 4 October 2026 Asqueel main at c0888b3 (0.4.0 on PyPI) GenroPy origin/develop at 5e7f02e8d774 Source of truth proposal 0001 and analyses 34–39

How to review

Most of what follows is not in the code yet. Asqueel 0.4.0 already runs queries and writes; the model and expression changes described here are design decisions taken one at a time, each compared with GenroPy before being written down.

Each section ends with questions. Please answer by section number, and tell us in particular:

  • choices you disagree with, and why;
  • GenroPy behaviour we forgot or misread;
  • uses in your applications that a decision would break.

Numbers about "real usage" come from the Sourcerer index of the team's repositories (for example: 150 hierarchical tables in 35 application repositories). Every legacy fact is backed by a file and line in the analysis documents linked at the end.

What Asqueel is

Asqueel keeps what makes GenroPy's database layer valuable, the model as the single place where tables, relations, calculated columns and their descriptions live, and makes it usable outside GenroPy.

  • Any Python application declares a model, opens a database and queries it with the same expression language GenroPy uses ($col, @rel.col, :param, macros).
  • A GenroPy application uses Asqueel through an adapter. The adapter translates GenroPy declarations (config_db, sysFields, table attributes, grid structures) into Asqueel declarations, and turns results back into the shapes GenroPy code expects.

Three things stay out of the Asqueel core and belong to the adapter or to the application: user interface, GenroPy package composition, and the web application's notifications.

Why the builders matter

GenroPy declares a model by calling methods that write attributes into a Bag. Asqueel declares it through a grammar built with genro-builders. Most differences in this document follow from what a grammar gives that loose attributes do not. This is the basis for every "why" box below.

Builders capabilityWhat it means for a modelGenroPy today

Typos such as rowCaption, captionField, partitioned_progetto_id exist in applications and are never read.

Declaring a model

GenroPy

class Table(object):
    def config_db(self, pkg):
        tbl = pkg.table('invoice', pkey='id',
                        name_long='!![en]Invoice',
                        caption_field='number')
        self.sysFields(tbl, counter='customer_id')
        tbl.column('number', size=':10')
        tbl.column('customer_id', size='22').relation(
            'sales.customer.id', mode='foreignkey',
            relation_name='invoices', onDelete='raise')
        tbl.column('total', dtype='N', size='12,2',
                   group='amounts.010')
        tbl.aliasColumn('customer_name',
                        '@customer_id.name')

Asqueel

class InvoiceModel:
    def configure(self, tables):
        tbl = tables.table('invoice', pkey='id',
                           name_long='Invoice',
                           caption_field='number')
        opts = tbl.options()
        opts.sys_fields()
        opts.auto_counter('customer_id')
        tbl.column('number', size=':10')
        tbl.column('customer_id', size='22').relation(
            'sales.customer.id',
            relation_name='invoices', on_delete='raise')
        amounts = tbl.colgroup('amounts', name_long='Amounts')
        amounts.column('total', dtype='N', size='12,2')
        tbl.aliasColumn('customer_name',
                        relation_path='@customer_id.name')
        return tbl

Columns are declared on the table Decided

As in GenroPy: tbl.column, tbl.formulaColumn, tbl.aliasColumn, tbl.index. The explicit form tbl.columns().column(...) of Asqueel 0.4 goes away. A name used by both a physical and a virtual column is an error; GenroPy's _override comes later with package composition. Supported column elements: column, formulaColumn, aliasColumn, subQueryColumn, pyColumn, compositeColumn. Not yet: joinColumn, bagItemColumn, toolColumn, aliasTable, subtable, localized columns.

One method, configure Decided

A table is declared in configure(self, tables), which returns the table. There is no config_db and no method per role. The GenroPy adapter calls the legacy config_db methods and translates them.

Column groups Decided

tbl.colgroup(name, name_long=..., col_*=...) declares a group once. A column joins it by being declared through the group, or with colgroup='name' on the table. Order is declaration order; there are no position numbers.

Why it differs. GenroPy's group='amounts.010' mixes grouping, ordering and interface visibility in one string, and the legacy colgroup counter never advances (every column gets .001). As a grammar element, a group has its own signature, defaults for its columns (col_*) and three checked errors: undeclared group, conflicting group, group declared twice.

Relations Decided

ElementDatabaseTarget
relation(...)FOREIGN KEY ... ON UPDATE CASCADE plus an index on the source columnsmust have a unique key; otherwise an error
weak_relation(...)no constraint; index on source and target columnstrusted to be unique; insensitive=True joins case-insensitively

Parameters keep GenroPy names in snake_case: related_column, relation_name, one_name, many_name, one_one, on_delete / on_update (Python actions on related records), on_delete_sql / on_update_sql (SQL actions of the foreign key), deferred, deferrable, initially_deferred. The outgoing relation is named after its column (@customer_id); x_name goes away.

Why it differs. In GenroPy a bare relation() is logical and mode='foreignkey' adds the constraint. In the eight largest application repositories, 3555 of 4134 relations (86%) use mode='foreignkey', so the common case becomes the short one. Two elements instead of a mode string give each kind its own closed parameter set: insensitive exists only where it can work, since a foreign key cannot compare case-insensitively. Links to non-unique targets, filtered relations and "one row by order" are left to virtualRelation (genropy_meta#1).

Composite keys and constraints Decided

One concept covers every key on several columns, as in GenroPy: compositeColumn(name, columns='a,b', unique=True). Its value is the serialized key ('["P1", 2024]'); it is selected by *; unique=True creates the multi-column UNIQUE; .relation(...) on a composite targets another composite. pkey always names one column, physical or composite. The constraint element leaves the model: CHECK constraints come back with the other native database objects (triggers, functions, views).

Every relation creates an index on its source columns unless they are already the leading columns of the primary key, a UNIQUE constraint or an index. There is no option to switch it off.

Questions

  1. Does any application depend on a logical relation() without foreign key in a way that weak_relation() would not cover?
  2. Are there uses of group='name.NNN' numbering that a declaration-order group cannot reproduce?
  3. Do you use constraint or CHECK in GenroPy models today?

Table features and options

GenroPy adds system columns and behaviours through sysFields(...) arguments, table attributes and base classes. Asqueel gathers table features in one visible block, tbl.options(), where each feature is an element describing one function. The functions are taken from what GenroPy offers, not from how it implements them.

The first three options Decided

OptionFunctionsGenroPy source
sys_fieldsgenerated primary key; insert and update timestamps; insert and update user; logical deletion; draftsysFields(id, ins, upd, user_ins, user_upd, ldel, draftField)
auto_counterrow numbering over the table or inside a foreign key; numbering inside a master that never reuses numberssysFields(counter=...), counter_<name>=, relidx
hierarchicaltree structure (next section)sysFields(hierarchical=...) and sub-options

Rules: at most one options per table; a feature outside it is an error; auto_counter may appear once per foreign key; dependencies between features are checked by the validator (for example hierarchical requires a single-column primary key).

Why it differs. Columns are the table's content and are declared directly on it; features describe how the table behaves and stay together as a separate block. Because each option is a grammar element, a typo is an error instead of a silently ignored attribute, and the generated grammar reference documents every option. In GenroPy the same knowledge is spread over sysFields keyword arguments (1617 calls, 58% without arguments) and table attributes read in many places.

Options registered by a package Open

Ten GenroPy packages in seven repositories add behaviour to tables of other packages the same way: the table declares an attribute owned by the package (multidb, wkfl, survey, e2l, tmsh_bookable, multi_tenant, ...) and the package reads it and mixes a class into the table. Asqueel needs a way for a package to register its own options, with signature and documentation. Package-wide defaults for every table are rare (dbstore policy in six packages) and are not a first need. Package-level Table classes in main.py (199 packages) never override write hooks or sysFields.

Hierarchical tables

Model: kept from GenroPy Decided

A parent_id relation plus materialized paths, physical, of the primary key (hierarchical_pkey) and of the declared fields (hierarchical_<field>). Moving a node or renaming a path field rewrites the subtree one child at a time with the Python triggers. Hierarchical tables are very static, so reads matter more than the cost of a rare rewrite. Sibling order is auto_counter('parent_id'); the tree sort key _h_count keeps GenroPy's 2 base-36 characters per level.

GenroPy

self.sysFields(tbl, hierarchical='description',
               counter=True, hierarchical_root_id=True)

Asqueel

opts = tbl.options()
opts.sys_fields()
opts.hierarchical('description')
opts.auto_counter('parent_id')

Corrections Decided

GenroPyAsqueelIssue
Moving a node under its own descendant is not checked on the server: endless cascadeErrorgenropy/genropy#1523
Parent and children are read with the draft and logical-deletion filters: a child of an archived parent becomes a rootRead without filters#1524
A moved node keeps its old sibling position; _h_count becomes empty above 1295 siblingsLast position under the new parent; explicit error at the 1296th sibling#1525
LIKE on paths without escape (ids contain _); no index usable by LIKE 'x%'Escaped LIKE; text_pattern_ops index on PostgreSQL#1526

The core will also offer subtree, ancestors and root with "node included" or "node excluded" stated explicitly. Today applications write the subtree filter by hand in three different forms. Their form will be decided together with GEP 1 and virtualRelation.

Open A null value in a path field; a / inside a path value; copyFromParent applied only on insert and move; _parent_h_* computed instead of physical. Not in the first increment: hierarchical_linked_to, virtual roots, hdepth (one to three uses each).

Writing expressions

The expression language is GenroPy's. Asqueel adds no alternative spelling; an unsupported form raises an error and never produces a different result.

FormMeaningStatus
$colcolumn of the current tableDecided
@customer_id.@state_id.namepath through relations; every relation segment starts with @Decided
:name, :env_namebound parameter; value from the environmentDecided
#THIS.<path>outer row in a correlated subquery, also inside sql_formulaDecided
#IN_RANGE(value, start, end)bounds included; a NULL bound is open; every contextDecided
#PERIOD($field, :p)period decoded by genro_toolbox.dates.parse_period; always >= from AND < day after endDecided, :p vs p open (#1509)
#ENVnot ported: :env_name replaces itDecided
#BAG, #BAGCOLS, TSQUERY, VECQUERY, #PREFlaterOpen
  • One parser, one resolver shared by queries, formulas, row policies and table.column(). Decided
  • A path that reaches many rows (for example @invoices from a customer) is an error. Its values come from GEP 1 relation functions: @invoices.count(), @invoices.sum($total). The parser reads that form from the start, so GEP 1 only adds the functions. Asqueel never compiles a join that multiplies the rows of the main table. Decided
  • table.column('missing') returns None, as in GenroPy; a path through a missing relation raises. Exceptions form one hierarchy rooted in GnrSqlException, one class per case. Decided

Why it differs. #THIS.@rel.col inside sql_formula is not expanded in GenroPy (genropy/genropy#1505); Asqueel resolves it like any other path. #PERIOD uses a half-open range so that a timestamp column includes the last day, which GenroPy's BETWEEN missed. The exception classes keep GenroPy names but share one root, so that except GnrSqlException catches all of them.

Questions

  1. Do you write intermediate relation segments without @ anywhere?
  2. Which macros beyond #THIS, #IN_RANGE, #PERIOD do your applications need first?

Grouping Direction

GenroPy's grouped view lets any user group any table view without code: drag fields, choose Break or an aggregate, see a flat list, a tree or a pivot, click a group to see its rows, save the view. Applications also use it from code (structures in 173 modules of 24 repositories). Asqueel's core will provide what that needs, for any interface:

  • a declarative, serializable grouping request (breaks, aggregates from a closed list, filters, pivot), compiled by the same resolver;
  • breaks on a hierarchical table that produce the intermediate nodes with their totals, at any depth;
  • roll-up rules computed in Python over a flat SQL GROUP BY (sum, count, min, max, weighted average, union of distinct values);
  • drill-down by condition instead of a list of primary keys; chaining, where the condition of a group filters a new grouping;
  • model metadata for the interface: relations, types, readable captions, hierarchical fields.

Why it differs. In GenroPy a break on hierarchical_description gives one node per full path ("Building Materials/Insulation/Batts") and no intermediate totals, because the tree builder never splits on / and the cell does not carry the hierarchical attribute. The legacy server inserts the aggregate name sent by the client directly into SQL; a closed list removes that. _pkeylist concatenates every key of a group, which grows with the data; a condition does not.

Questions

  1. Which grouping features do your users rely on most: tree, pivot, saved views, dashboards?
  2. Is drill-down by condition acceptable everywhere, or do some screens need the explicit key list?

Primary keys Open

Analysis only. In GenroPy newPkeyValue(record) calls pkeyValue(record), which tries six rules in order: composite key, numeric max + 1, UUID when there is no record, pkey_columns, __syscode, 22-character text UUID; otherwise it returns None. Four applications override newPkeyValue (a code from a counter, a fixed key for a one-row table, _ replaced for bank imports, a random code retried until unique).

Defects to avoid: max + 1 without a lock; insertMany giving every record the same numeric key; pkey_columns collisions when values are None or contain the joiner; a silent None when no rule applies. Asqueel today does not generate keys: it inserts the values given and reads back RETURNING.

Questions

  1. Which key types do new tables use: 22-character UUID, serial, codes?
  2. Do you need the per-table override point, or would declared rules cover your cases?

Writes and Python actions

Python first Decided: when a behaviour can live in Python or in SQL, the Python one prevails; names follow, the short name is the Python action and the _sql suffix the SQL one (on_delete versus on_delete_sql). The full write cycle (field triggers, counters, cascades on related records, protections) is still to be designed; the adapter obligations below list the GenroPy protocol it must reproduce.

The GenroPy adapter

The adapter is how existing GenroPy code keeps working. It is a separate layer: package composition, application rules and notifications do not go into the PostgreSQL or SQLite driver.
